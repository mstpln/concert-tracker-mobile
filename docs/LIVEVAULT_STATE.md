# LiveVault Current State

## Repository and current build

LiveVault is `mstpln/concert-tracker-mobile`. GitHub `main` is authoritative. Production is a GitHub Pages static PWA backed by the authenticated Cloudflare Worker `concert-tracker-api` and private R2 bucket `concert-tracker-data`.

For historical build detail before v126, use Git history and `docs/LIVEVAULT_DECISIONS.md`; the durable current-state entries below describe the recent implemented architecture.

## v126 UI responsiveness state

PR #130 on `perf/ui-responsiveness-v126` addresses the collection-size responsiveness regression exposed after the production band catalogue grew. The investigation found a concrete hot path in My Bands: every visit rebuilt hundreds of band rows, and activity classification called the legacy latest-show helper once per band, rescanning the entire concerts array each time. That made the screen scale as bands multiplied by concerts before DOM reconstruction costs were counted.

v126 keeps the existing renderer authoritative but adds a narrow My Bands performance layer. Each invocation builds a fresh latest-concert-date index in one concerts pass. The render key contains only fields that can affect the visible My Bands list or its filters/activity badges (band ID/name/genre/muted/transient enrichment state/last-known date, latest indexed concert date, filter settings, inactivity threshold and current calendar day). If that complete visible-state key is unchanged and the existing DOM is still present, the hundreds of existing rows and their listeners are reused instead of rebuilt. Any visible band, genre, mute, activity-date, filter or day change produces a new key and runs the original renderer. Large provider/research histories are intentionally excluded because they do not render on this root list. No listening state or provider object is cached.

Synthetic unit coverage validates latest-date equivalence, stored-date precedence, 400-band/5,000-concert scaling, unchanged-view reuse, visible-state invalidation and empty-DOM recovery. A browser regression uses the same 400-band/5,000-concert synthetic shape and proves that an unchanged second render produces no DOM mutation while a visible band-name change forces a real rerender. `APP_VERSION`, `CACHE_NAME_LITERAL` and deterministic build facts are synchronized at v126. The build changes no production JSON, provider behavior, Worker/Cloudflare configuration, secrets, production workflows or deployment.

## v127 general responsiveness state

PR #131 on `perf/general-responsiveness-v127` removes the largest confirmed remaining navigation bottleneck in My Concerts and band-profile concert rendering. The legacy listening-summary path could rescan the complete private listening archive once per concert card, multiplying a 250,000+ event history across dozens of cards. v127 builds one temporary in-memory per-band listening index at the start of each affected render, sorts each band bucket once, records prefix duration/listen totals, and answers each concert listening window with binary-search lookups instead of rescanning the source archive. The index exists only for the active render and is discarded immediately afterward; the authoritative listening event array is restored synchronously.

The performance layer deliberately avoids a long-lived cache so newly loaded, activated or changed listening history cannot leave stale concert summaries. Existing GAU1 listening-window semantics remain authoritative through `LiveVaultV72.concertListeningWindow`; the v127 layer only replaces the repeated aggregation work. The final wrapper is installed after the asynchronous v72 compatibility bootstrap so the optimized row owner wraps the canonical legacy owner once and does not duplicate visible listening rows. No stored data, schema, provider ownership, Worker behavior, Cloudflare configuration, production workflow or production data is changed.

Synthetic unit coverage exercises a 250,000-event / 400-band history and proves that 75 concert-window queries do not rescan the source archive. Desktop and mobile Chromium QA use a 50,000-listen / 75-concert synthetic browser shape, verify equivalent visible listening summaries, confirm the source listening array is restored, and cover the existing GAU1 upcoming/recent-past listening-window regression. `APP_VERSION`, `CACHE_NAME_LITERAL` and deterministic build facts are synchronized at v127. PR #131 authorizes no production provider call, production workflow, R2 write, deployment, merge or auto-merge.

## v128 NB1 concert-card polish state

NB1 is implemented on `feature/nb1-concert-card-polish-v128` in PR #133 as v128. Past and upcoming My Concerts cards and the Band Detail hero use a thin 1 px neutral-grey outline around the actual artist image. Upcoming My Concerts cards keep the existing blue distance metadata line and append the approved countdown inline with a dot separator, for example **59 km away · 69 days until concert**. The close-date labels are **Today** and **Tomorrow**; past cards receive no countdown, and an upcoming card without distance still receives the countdown as the same blue metadata treatment.

The countdown is derived at render time from the stored concert date and does not add or modify concert data. The v127 renderer/performance layer remains authoritative; NB1 extends that final row renderer rather than adding a competing wrapper, and the image-border style is installed once with the same layer. Stable IDs, attendance, venue/ticket fields, listening summaries, user-owned fields, provider state, Worker/storage behavior and production data remain unchanged.

Focused Node coverage verifies Today/Tomorrow/day-count labels, inline distance/countdown rendering, no change to past cards and the no-distance fallback. ## v134 missing artist-image maintenance state

The `codex/fix-artist-image-maintenance` branch adds a permanent low-priority artist-image lane to the existing Monday/Wednesday/Friday structured research run. A band is considered only when the established visible-image precedence has no usable manual `photoUrl`, trusted Spotify image or trusted official-site image. Existing usable artwork is an absolute exclusion, duplicate trusted Spotify identities fail closed, and no user-owned image field is written or replaced.

Planning prefers the new private Worker object `listening/band-activity.json`. The browser derives it from locally restored listening history and publishes only stable band IDs, mutually exclusive 14-day / 3-month / 1-year / older counts, ordinal recency ranks inside each bucket, a catalogue fingerprint and aggregate freshness metadata. Exact listen timestamps never leave private browser storage. It contains no artist or track names, individual listen IDs, URLs or raw observations. Its schema is a strict allowlist at the root, record and bucket levels; unknown fields are rejected on write and revalidated before any read, so a malformed stored object cannot smuggle raw listening fields to automation. The automation credential may read this one aggregate but remains forbidden from all listening manifests, archives and other listening objects. Planning binds the aggregate to the exact current stable-ID set as well as its fingerprint. Missing, stale, malformed or catalogue-mismatched aggregate state falls back to deterministic no-listening ordering rather than disabling eventual image maintenance. The synthetic QA build removes the publisher script from its generated HTML, so it cannot access a production connection.

At most ten unique bands are selected and independently re-capped at execution, ordered by exclusive listening bucket, then trusted-Spotify-ID availability, listen count, most recent activity and stable band ID. A trusted ID goes directly to exact `GET /v1/artists/{id}` without name search. A missing ID first uses the existing conservative identity resolver; artwork is not trusted from search results, and an exact artist request runs only after identity becomes trusted. Newly resolved duplicate IDs become review state and receive no artwork. Response identity must match exactly and every stored image must have an HTTPS URL and valid optional dimensions. Empty image arrays are retained as a documented no-image result and retried after 180 days, or immediately after a trusted identity change, so a later Spotify artwork addition can eventually be discovered without refreshing bands that already have visible artwork. Transient failures remain retryable after 24 hours. Provider state remains under `band.musicbrainz.spotify`, while `photoUrl` remains user-owned.

DAB6 persisted Spotify circuit handling, UsageTracker accounting/pacing, DAB7 lease admission and strict conditional band writes remain authoritative. Network and 5xx exact lookups receive one bounded retry; 429/quota outcomes at either identity or exact-image stage use DAB6 and stop the lane. Latest manual artwork, identity changes and write conflicts win. Provider merges retain unknown provider fields, while provider-specific reviewed state remains whole-object authoritative. `APP_VERSION`, `CACHE_NAME_LITERAL` and deterministic build facts are synchronized at v134. This implementation creates no production aggregate, makes no live provider call, runs no production workflow, changes no Cloudflare production configuration, deploys nothing and merges nothing.

## v135 provider and release cleanup state

PR #141 on `feature/provider-release-cleanup-v135-final` retires dedicated album/EP/single release monitoring from the scheduled structured workflow and removes Releases from the visible Alerts and Band Detail surfaces. Concert alerts, Listening, Data, predicted playlists, historical setlist song links, listening artwork and artist-image maintenance remain in scope. Existing structured release state is preserved for backward compatibility rather than destructively migrated or deleted.

ListenBrainz normalization retains bounded validated HTTPS URL relationships plus release-group and Cover Art Archive identifiers in the immutable listening event contract. That evidence remains inside the private listening boundary. The ordinary GitHub structured-research credential is not widened to read private listening archives, so scheduled historical setlist-link resolution reuses provider-neutral evidence only when it is already present on the song/evidence object supplied to the resolver; it does not fetch private listening history. This preserves the established least-privilege boundary instead of creating a new cross-store join.

Non-playlist Spotify link resolution now has a fail-closed local resolver for trusted exact Spotify IDs/URLs and validated ListenBrainz or MusicBrainz Spotify URL relationships. Conflicting exact relationships are quarantined from reuse. Playlist matching remains separate and unchanged. Spotify observability is aggregate-only by lane, endpoint family, outcome and circuit event; it contains no track/artist IDs, query text, URLs, tokens or provider payloads. Diagnostics are reset when each scheduled `UsageTracker` instance is loaded so token attribution, circuit-start state and endpoint counts describe the current run rather than accumulating misleading state across runs.

`APP_VERSION`, `CACHE_NAME_LITERAL` and deterministic build facts are synchronized at v135 and remain on that version for focused pre-merge corrections. Development and automated QA use synthetic fixtures and the QA fake backend only. PR #141 authorizes no production provider call, private listening read, production workflow, production data/R2 write, Cloudflare production change, deployment, merge or auto-merge.
